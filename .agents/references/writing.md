# 記事執筆フェーズ

検証結果をもとに、ブログ記事の下書きを作成するフェーズ。

## フロー概要

```
Step 1: 状況確認と案内 — 検証結果・ブログポイントを要約し、執筆方針を確認する
Step 2: 下書き作成 — テンプレートに沿って記事を書き、ユーザーのフィードバックで仕上げる
Step 3: 下書きレビュー — サブエージェントによる第三者レビュー（任意）
Step 4: フェーズ完了確認 — ユーザーの合意を得て draft_completed へ
```

## Step 1: 状況確認と案内

NOTES.md・poc/・project.yaml を確認し、以下のテンプレートでユーザーに案内する:

> 記事執筆フェーズです。検証結果を確認しました。
>
> **記事の概要:**
> - タイトル: （project.yaml から）
> - 読者ターゲット: （NOTES.md の企画から）
>
> **ブログポイント（NOTES.md より）:**
> - （ブログポイントを箇条書きで要約）
>
> この内容で記事の下書きを作成します。記事の構成や書き方について希望はありますか？なければ、テンプレートに沿って書き始めます。

## Step 2: 下書き作成

`blog/<article-id>/draft.md` にテンプレートに沿って記事を書く。

テンプレート: [templates/draft.md](../templates/draft.md) （`.agents/templates/draft.md`）
テンプレートはユーザーが自由にカスタマイズしている可能性がある。テンプレートの構成に従うこと。
テンプレート内の HTML コメント（`<!-- ... -->`）にはユーザーからの指示が書かれている。各セクションに何を書くべきかの指針になるので、コメントの内容に従って執筆する。

下書きを作成したらユーザーに確認を依頼する。フィードバックがあれば修正し、合意が得られるまで繰り返す。

下書きが完成したら、レビューを提案する:

> 下書きが完成しました。
>
> 下書きの内容をサブエージェントにレビューさせることをお勧めします。記事の正確性や読みやすさを第三者目線でチェックできます。
> レビューしますか？

ユーザーがレビューを希望したら Step 3 へ。スキップする場合は Step 4 へ進む。

## Step 3: 下書きレビュー

サブエージェント（別コンテキスト）に下書きのレビューを依頼する。

サブエージェントには `blog/<article-id>/draft.md` と `NOTES.md` を渡し、以下の観点で評価させる:

- 検証結果と記事の内容に齟齬がないか
- 記事の構成は読みやすいか
- ブログポイントが漏れなく記事に反映されているか

### レビュー結果の提示

レビュー結果は**必ず表形式でユーザーに提示する**。エージェントが勝手に修正してはいけない。

| # | 指摘内容 | 修正方針 |
|---|---------|---------|
| 1 | （サブエージェントの指摘を要約） | （エージェントが考えた修正案） |
| 2 | ... | ... |

提示後、以下のテンプレートで案内する:

> サブエージェントのレビュー結果です。上記の修正方針で進めてよいでしょうか？
> 修正方針を変えたい項目や、対応不要と判断する項目があれば教えてください。

ユーザーの合意を得てから修正を実施する。

## Step 4: フェーズ完了確認

まず機械チェックを実行する:

```bash
.agents/scripts/check-phase.sh <article-id> draft_completed
```

このスクリプトは project.yaml への記事登録、draft.md の存在、本文が参照する画像の存在、textlint の合格を検証する。NG が出た場合は解消してから再実行し、合格を確認する。

合格したら、以下のテンプレートで案内する:

> 記事執筆フェーズはこれで完了でよいでしょうか？
> よければ phase を `draft_completed` に更新します。次は WordPress への投稿に進むことができます。

ユーザーが合意したら `project.yaml` の `phase` を `draft_completed` に設定する。

## phase 遷移条件

`draft_completed` に遷移するには、以下がすべて満たされていること:

- `blog/<article-id>/draft.md` が作成されている
- `.agents/scripts/check-phase.sh <article-id> draft_completed` が合格している
- ユーザーが下書きの内容を確認し、合意している
- サブエージェントによるレビューが完了している（ユーザーがスキップした場合は不要）
- レビューを実施した場合、指摘事項について修正方針を合意し反映済みである
- ユーザーがフェーズ完了に合意している

## リファレンス

### 書き方のルール

#### コードブロック

- 言語指定を必ず付ける（```typescript, ```yaml 等）
- コードブロックの前に、何を見せるかを1文で説明する
- コードブロックの後に、ポイントや注意点を箇条書きで説明する
- 長すぎるコードは要点を抜粋し、全体はGitHubリポジトリへのリンクで補足する

#### 画像

- 画像は `blog/<article-id>/images/` に配置する
- Markdown内では相対パスで参照する: `![説明](images/xxx.png)`
- WordPress MCP が自動でアップロード・URL置換する
- 説明的なファイル名を付ける（連番は使わない。例: `grafana-dashboard-overview.png`）

**POC の画像を記事に使う場合:**

`poc/images/` から `blog/<article-id>/images/` にコピーする。NOTES.md の `-> ブログ:` マーカーが付いた画像を確認し、記事に必要なものを選ぶ。

**追加のスクリーンショットが必要な場合:**

記事を書いている途中で、POC にはない画像が必要になることがある（手順の途中画面、設定画面、エラー画面など）。その場合は `screenshot` スキルで撮影し、`blog/<article-id>/images/` に直接保存する。

#### リンク

- 公式ドキュメントや参考記事は積極的にリンクする
- GitHubリポジトリの URL は目立つように単独行で記載する

#### その他

- 実際に試した結果に基づいて書く（推測で書かない）
- ハマりポイントや注意点は明示する（NOTES.md の `-> ブログ:` マーカーを参考に）

### WordPress MCP で使えない記法

以下の Markdown 記法は WordPress MCP で正しく変換されないため、使わないこと:

- **コードブロックのファイル名指定**: ````typescript:app.ts` のような記法は効かない。ファイル名はコードブロックの直前にテキストで書く
- **タスクリスト**: `- [ ]` / `- [x]` は使わない。通常のリストで代替する
- **H1 はタイトル専用**: H1 は投稿タイトルに自動変換され本文から除去される。本文の見出しは H2 以下を使う
