# アイデア・企画フェーズ

## フロー概要

```
Step 1: ヒアリング — ユーザーのアイデアを聞く
Step 2: 企画案の提示 — 読者・目的・差別化・検証ポイントを提案
Step 3: 検証計画の提示 — 何を・どうやって・何で検証するかを提案
Step 4: 企画レビュー — サブエージェントによる第三者レビュー
Step 5: フェーズ完了確認 — ユーザーの合意を得て idea_completed へ
```

## Step 1: ヒアリング

ユーザーにアイデアを自由に話してもらう。以下のテンプレートで案内する:

> どのような記事にしたいですか？
> 検証したいこと、興味があること、気になっている技術など、何でも自由に教えてください。
>
> それをもとに、私が以下の案を整理します:
> - **読者ターゲット** — 誰に向けた記事か
> - **記事のゴール** — 読者が何を得られるか
> - **差別化ポイント** — 既存記事との違い
> - **検証で確認すべきこと** — 記事を書くために検証が必要な項目

ユーザーの回答が曖昧な場合は、具体化するための質問を投げかける。十分な情報が集まるまでこのステップを繰り返す。

## Step 2: 企画の整理

ユーザーとキャッチボールしながら企画を詰めていく。企画が整理できたら、以下のテンプレートで最終確認する:

> 企画を整理しました。
>
> - **読者ターゲット**: （整理した内容）
> - **記事のゴール**: （整理した内容）
> - **差別化ポイント**: （整理した内容）
> - **検証で確認すべきこと**: （整理した内容）
>
> この企画案でいかがでしょうか？
> 修正したいところがあれば教えてください。質問があれば何でも聞いてください。
>
> この内容でよければ、次は検証計画（何を・どうやって・何で検証するか）を決めていきます。技術スタックや検証の進め方に希望はありますか？なければ、私が案を提示します。

ユーザーが修正を求めた場合は、修正してテンプレートで再提示する。合意が得られるまでこのステップを繰り返す。

## Step 3: 検証計画の提示

検証に入る前に、計画を確定する。曖昧なまま検証に入ると、途中で方針転換が必要になりコストが大きくなる。

以下の3点を整理して提案する:

### 検証のゴール

Step 2 の「検証で確認すべきこと」を具体的な検証項目に落とし込む。

- 何を検証するか（ゴール）
- どう検証するか（手順）
- 想定される成果物

### 技術スタック

検証に使う技術構成について、選択肢とトレードオフを提示する:

- プログラミング言語とバージョン
- フレームワーク・ライブラリとバージョン
- ビルドツール（Gradle, Maven, npm 等）
- デプロイ方式（コンテナ、Zip、マネージドランタイム等）
- テスト方法（ローカルテスト、結合テスト等）

提案後、以下のテンプレートで案内する:

> この検証計画で進めるのはどうでしょうか？
> 検証の進め方や技術スタックで変更したいところがあれば教えてください。
>
> この内容でよければ、企画と検証計画を NOTES.md に記録します。

合意が得られたら、以下を実行する:

1. `NOTES.md` の `## 企画` セクションに読者ターゲット・ゴール・差別化・検証項目を記録
2. `NOTES.md` の `## 方針` セクションに検証のゴール・手順・成果物を記録
3. `NOTES.md` の `## 技術スタック` セクションに技術構成と選定理由を記録
4. `project.yaml` の `articles` に記事を追加する（まだ phase は設定しない）

記録方法の詳細は [notes-guide.md](notes-guide.md) を参照。

### project.yaml の更新例

```yaml
articles:
  - id: 01-getting-started
    title: "記事タイトル"
```

記録完了後、以下のテンプレートでレビューを提案する:

> NOTES.md と project.yaml に記録しました。
> この企画と検証計画をサブエージェントにレビューさせることをお勧めします。第三者目線で実現可能性やスコープの妥当性をチェックできます。
> レビューしますか？

ユーザーがレビューを希望したら Step 4 へ。スキップする場合は Step 5 へ進む。

## Step 4: 企画レビュー

サブエージェント（別コンテキスト）に企画のレビューを依頼する。壁打ち相手として議論した後では肯定的なバイアスがかかりやすいため、第三者目線での批判的な評価を得ることが目的。

サブエージェントには `NOTES.md` の `## 企画`・`## 方針`・`## 技術スタック` セクションを渡し、以下の観点で評価させる:

- 技術的に実現可能か（既知の制約や未対応機能はないか）
- 検証の工数は妥当か（スコープが広すぎないか）
- 記事としての差別化は十分か（既存記事と比べて新しい価値があるか）

### レビュー結果の提示

レビュー結果は**必ず表形式でユーザーに提示する**。エージェントが勝手に修正してはいけない。

| # | 指摘内容 | 修正方針 |
|---|---------|---------|
| 1 | （サブエージェントの指摘を要約） | （エージェントが考えた修正案） |
| 2 | ... | ... |

提示後、以下のテンプレートで案内する:

> サブエージェントのレビュー結果です。上記の修正方針で進めてよいでしょうか？
> 修正方針を変えたい項目や、対応不要と判断する項目があれば教えてください。

ユーザーの合意を得てから修正を実施し、NOTES.md に反映する。

## Step 5: フェーズ完了確認

すべてのステップが完了したら、以下のテンプレートで案内する:

> アイデア・企画フェーズはこれで完了でよいでしょうか？
> よければ phase を `idea_completed` に更新します。次は検証（PoC）に進むことができます。

ユーザーが合意したら `project.yaml` の `phase` を `idea_completed` に設定する。

## phase 遷移条件

`idea_completed` に遷移するには、以下がすべて満たされていること:

- NOTES.md の `## 企画` に読者ターゲット・ゴール・差別化・検証項目が記録されている
- NOTES.md の `## 方針` に検証のゴール・手順・成果物が記録されている
- NOTES.md の `## 技術スタック` に技術構成と選定理由が記録されている
- サブエージェントによる企画レビューが完了している（ユーザーがスキップした場合は不要）
- レビューを実施した場合、指摘事項について修正方針を合意し反映済みである
- ユーザーの疑問や懸念が解消されている
- ユーザーがフェーズ完了に合意している
